# Internationalization (i18n)

Status: **architectural decision** ([ADR-008](../adr/ADR-008-i18n-from-start.md)): full German + English support from the first release, in UI **and** content.

## Locales

- `de` (default) and `en` for MVP. Adding a locale later (e.g. `fr` for Swiss visitors) must be a content + configuration task, not a refactor — everything below is locale-count-agnostic.
- Locale routing: path prefix `/de/…`, `/en/…` with localized path segments and slugs ([../ux/information-architecture.md](../ux/information-architecture.md#url-structure-decision)). First visit negotiates from `Accept-Language`; user choice persists locally and always wins.

## Three localization layers

| Layer | Content | Mechanism |
|---|---|---|
| UI strings | Labels, buttons, errors, filter names | `next-intl` message catalogs (`messages/de.json`, `messages/en.json`), typed keys, CI check for missing keys |
| Vocabulary labels | Categories, interests, audiences, regions, enums | Localized label columns on vocabulary tables ([../data/tag-and-filter-taxonomy.md](../data/tag-and-filter-taxonomy.md)); served with API responses |
| Attraction content | Names, summaries, descriptions, practical notes, closure reasons | `AttractionLocalization` rows ([domain-model.md](domain-model.md#attractionlocalization)) |

## Content localization rules (decision)

1. **German is the source locale** for researched content (sources are predominantly German); English is produced by the translation step of the research workflow — **only after fact verification** ([../data/research-workflow.md](../data/research-workflow.md), [../research/prompts/translation.md](../research/prompts/translation.md)).
2. **Publication requires both locales.** An attraction cannot be `PUBLISHED` with a missing or `NEEDS_REVIEW`/`STALE` localization (invariant in [domain-model.md](domain-model.md#attraction-aggregate-root--stable-editorial-data)).
3. **No machine-translation at request time.** All translations are stored, reviewed content.
4. Proper names are not translated; summaries are transcreated for clarity, not literal. English content must explain regional concepts (Kur, Hallenbad, Bodenseeschifffahrt) rather than assume them — see translation prompt.

### Translation invalidation {#translation-invalidation}

When a source-locale text field changes (editor or approved change proposal), the counterpart localization's `translationState` flips to `STALE` automatically; stale localizations appear in the admin work queue and block re-publication of the affected texts until resolved. `translationState` machine: `SOURCE` (this locale is the origin) · `TRANSLATED` · `NEEDS_REVIEW` (fresh machine-assisted draft) · `STALE`.

## Formatting

- Dates/times: locale-aware via `Intl` (`de`: 24 h, `DD.MM.YYYY`; `en`: locale-appropriate). All logic in UTC; display in the lake's time zone (CET/CEST — identical across DE/CH/AT).
- Currency: **never converted** — Swiss attractions show CHF, German/Austrian show EUR, always with an ISO code and locale-formatted number (`Intl.NumberFormat`). A static guide explains currencies (persona P2).
- Distances: metric everywhere (`km`/`m`) in both locales (established for travel content; imperial toggle is a non-goal).
- Public holidays: country/subdivision-specific calendars, never assumed shared ([domain-model.md](domain-model.md#opening-hours)).

## SEO integration

`hreflang` alternates on every public page; localized sitemaps; localized meta/OG tags. Details: [../operations/analytics-and-seo.md](../operations/analytics-and-seo.md#seo).

## Testing

Localization test set in [../quality/testing-strategy.md](../quality/testing-strategy.md): no hardcoded strings (lint rule), catalog completeness (CI), slug round-trips, currency/holiday correctness per country, language-switch state preservation (e2e), pseudo-locale layout check for text expansion (German is ~30 % longer than English; components must not truncate).
